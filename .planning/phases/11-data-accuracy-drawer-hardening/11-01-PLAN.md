**DATA-02 (AOV gross/net mismatch — per D-01):**

In `computeAffiliateUpsells` (line 382-423), the upsellMap accumulates `e.gross += t.grossAmount` (line 402) but `totalAOV` is computed from `totalNet` (net amounts). The `aovContribution` at line 408 divides `e.gross / frontSalesCount` — this is the mismatch.

Fix: Change the upsellMap to also accumulate net amounts. Update the Map type to `{ quantity: number; gross: number; net: number }`. Initialize with `{ quantity: 0, gross: 0, net: 0 }`. Add `e.net += t.netAmount` in the loop. Then at line 408, change `e.gross / frontSalesCount` to `e.net / frontSalesCount`.

Keep `e.gross` in the map and in the return value (it's used for sorting and display of gross totals) — only the `aovContribution` calculation changes to use `e.net`.

**DATA-03 (regex word boundary — per D-02):**

In `classifyUpsellProduct` (line 336-344), the issue is ORDERING: "down10" matches `/^down\s?1\b/i` because `\b` sits between "1" and "0"... actually wait — `\b` after "1" would NOT match if "0" follows because "10" is still word chars. Let me re-examine.

Actually the real issue: `/^down\s?1\b/i` — the `\b` is after "1". If input is "down10", the regex tries to match "down" then optional space then "1" then word boundary. Since "10" follows "down", "1" is at position 4-5, and the next char "0" is a word char — so `\b` does NOT fire. The regex should NOT match "down10".

However, looking more carefully at potential inputs like "Down 1 - Slimjara" vs "Down 10 - Slimjara": the pattern `/^down\s?1\b/i` would match "Down 1 " (space after 1 is a word boundary). And "Down 10" — after matching "down", optional space matches nothing, then "1" matches the "1" in "10", then `\b` — but next char is "0" which is `\w`, so `\b` fails. So the regex seems correct...

BUT the context says there's a bug. The issue may be with the `\s?` making it match "down1" within "down10": "down" matches, `\s?` matches zero chars, "1" matches the first "1" in "10", then `\b` — next char is "0" (word char), previous matched is "1" (word char) → no boundary → regex fails. So it should be fine...

The safest fix regardless: reorder patterns from longest to shortest (down10 before down1) and add explicit patterns for double-digit variants. Add these BEFORE the single-digit patterns:

```typescript
if (/^down\s?10\b/i.test(productName)) return "down10";
// ... existing down1, down2, down3
```

Also add `up10`, `up4`, etc. if they exist in real data. Since we cannot know all variants, the safest approach is: add explicit higher-number patterns (up4-up10, down4-down10) that return the number as-is, OR more defensively, change the single-digit regexes to use a negative lookahead to ensure no digit follows:

Change all single-digit patterns to use `(?!\d)` instead of `\b`:
- `/^up\s?1(?!\d)|^up\(1\)/i` for up1
- `/^up\s?2(?!\d)|^up\(2\)/i` for up2
- `/^up\s?3(?!\d)|^up\(3\)/i` for up3
- `/^down\s?1(?!\d)/i` for down1
- `/^down\s?2(?!\d)/i` for down2
- `/^down\s?3(?!\d)/i` for down3

This ensures "down10" never matches "down1" pattern, regardless of what follows.

**HARD-01 (per D-07, D-08):**

In `src/hooks/useAffiliateTags.ts`, the `writeTagsToStorage` function (line 17-19) calls `localStorage.setItem` without any error handling. When localStorage is full, this throws a `QuotaExceededError` that propagates up uncaught.

Fix: Wrap the `localStorage.setItem` call in a try/catch block. On any error (including QuotaExceededError), fail silently — do NOT re-throw, do NOT show a notification (per D-08). The function return type remains `void`.

```typescript
export function writeTagsToStorage(tags: Record<string, string[]>): void {
  try {
    localStorage.setItem(LS_KEY, JSON.stringify(tags));
  } catch {
    // Silently ignore quota errors — tags are non-critical
  }
}
```

Add a test in `useAffiliateTags.test.ts` that mocks `localStorage.setItem` to throw a `DOMException` (QuotaExceededError) and verifies `writeTagsToStorage` does not throw.
